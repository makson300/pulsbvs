# Пульс БВС — требования к обезличенным журналам DJI Agras T40

**Статус:** запрос данных для исследования формата; не описание уже поддержанного лога.

## 1. Цель

Получить минимальный, воспроизводимый и безопасный набор реальных журналов, который позволит подтвердить источник, схему, единицы и границы применимости отдельного адаптера DJI Agras T40. До этого этапа проект поддерживает только общий frontend-разбор CSV/TXT/KML; DAT/ZIP не считаются поддержанными для аналитики или истории.

Результат исследования должен позволить для каждого будущего вывода ответить:

1. из какого поля какого источника взято значение;
2. какая единица и диапазон подтверждены;
3. какой парсер и профиль правила использованы;
4. какие данные отсутствовали;
5. почему вывод имеет конкретную степень уверенности.

## 2. Что нужно передать по каждому образцу

### 2.1. Сам файл

Передавать **обезличенную копию** оригинала в исходном расширении. Предпочтительны небольшие, но реальные образцы с сохранённой структурой, заголовками, типами строк и кодировкой. Не преобразовывать DAT/ZIP в текст «для удобства» и не переименовывать расширение: это ломает исследование формата.

Для каждого файла нужен отдельный паспорт с полями:

| Поле | Требование |
| --- | --- |
| `sample_id` | локальный нейтральный идентификатор, например `t40-sample-001` |
| дата получения | месяц/год достаточно, если точная дата чувствительна |
| тип и расширение | как передано источником: CSV, TXT, KML, DAT, ZIP и т. п. |
| способ выгрузки | точное название инструмента и действия пользователя, если известно |
| исходная система | дрон, пульт, DJI Assistant 2 for MG, SmartFarm или другое; не угадывать |
| модель аппарата | подтвердить `DJI Agras T40` либо указать, что неизвестна |
| версия ПО дрона | если доступна |
| версия ПО пульта | если доступна |
| версия приложения/экспортера | если доступна |
| кодировка и разделитель | если известны; иначе указать «неизвестно» |
| часовой пояс временных меток | если известен; иначе указать «неизвестно» |
| описание полёта | кратко: контрольный/рабочий, с нагрузкой или без; без адресов и персоналий |
| ожидаемые события | например, «виден нагрев» только как операторская заметка, не как подтверждённый факт |
| разрешение на использование | разрешено только исследование и локальные тесты / разрешены публичные обезличенные фикстуры |

Не нужно сообщать пароль, токены, учётные данные DJI, внутренние ссылки, координаты объекта, ФИО пилотов или коммерчески чувствительные сведения.

### 2.2. Минимальная выборка

Для исследования полезны как нормальные, так и проблемные записи. Если доступны, передать по одному обезличенному образцу каждого вида:

1. обычный завершённый полёт T40;
2. полёт с доступными батарейными полями;
3. полёт с доступными напряжениями отдельных ячеек;
4. полёт с доступной температурой батареи;
5. запись с предупреждением/ошибкой, **только** вместе с контекстом его появления и дословным значением поля;
6. KML/SmartFarm маршрут для проверки границы «только маршрут»;
7. DAT и/или ZIP в исходном виде, если есть законное разрешение на исследование формата;
8. при наличии — один заведомо неполный или повреждённый экспорт для проверки безопасной обработки ошибок.

Ни один пункт не обязателен ценой раскрытия чувствительных данных. Обычный обезличенный CSV/TXT с паспортом полезнее неподтверждённого «дампа» без происхождения.

## 3. Поля, которые нужно зафиксировать, а не предполагать

Для каждого образца составляется таблица «исходное имя поля → тип → единица → диапазон → примечание». Не переносить универсальные алиасы текущего демо как утверждённую T40-схему.

### 3.1. Контекст и идентификация

Нужны, если реально доступны:

- марка/модель аппарата;
- безопасный псевдоним или хэш дрона;
- безопасный псевдоним или хэш батареи;
- идентификатор полёта/миссии;
- версия ПО дрона, пульта и экспортера;
- время начала/окончания, часовой пояс и признак UTC/локального времени.

Серийные номера не нужны для первой передачи. Если без стабильной идентификации нельзя проверить связь записей, передавать согласованный необратимый псевдоним, а не настоящий серийный номер.

### 3.2. Полёт и маршрут

Фиксировать при наличии:

- timestamp;
- широту/долготу;
- высоту и её вид (относительная, абсолютная, над точкой взлёта — если известен);
- скорость и направление;
- режим полёта;
- продолжительность/границы сегментов;
- нагрузку, распыление и условия работы — только если поле действительно есть и единица понятна.

Координаты относятся к чувствительным данным. Их допустимо округлить/сместить одинаковой трансформацией в пределах файла, если это не меняет формат и не создаёт фиктивных значений. Способ обезличивания фиксируется в паспорте.

### 3.3. Батарея

Нужны реальные имена и единицы полей для:

- процента заряда;
- напряжения всего пакета;
- тока и его знака/направления;
- температуры батареи;
- напряжений всех отдельных ячеек и их количества;
- количества циклов и момента, на который оно относится;
- состояния батареи;
- предупреждений, кодов ошибок и исходных сообщений.

Особенно важно подтвердить:

- вольты или милливольты;
- градусы Цельсия или другая шкала;
- амперы или миллиамперы;
- момент измерения и частоту точек;
- является ли значение мгновенным, средним, минимумом/максимумом или расчётным;
- что именно обозначает отрицательное значение, ноль, пустая строка и специальный код.

### 3.4. Ошибки и предупреждения

Поле warning/ошибки не является готовой диагностикой. Для каждого реального значения требуется:

- точное исходное имя поля;
- дословное значение из лога, без нормализации «на глаз»;
- тип: текст, код, битовая маска, число или неизвестно;
- связь со временем/строкой и другими полями;
- источник расшифровки: официальная документация, интерфейс DJI с версией или подтверждённое наблюдение;
- известный безопасный смысл и неизвестные части.

До этой фиксации запрещено превращать любые CSV warning-строки в `BATTERY_DEVICE_ERROR`. Ошибка может относиться не к батарее или иметь иную кодировку.

## 4. Обезличивание и приватность

Перед передачей убрать или заменить согласованными псевдонимами:

- ФИО, телефоны, email и логины;
- серийные номера дрона, батареи, пульта и SIM;
- идентификаторы аккаунтов, токены, ключи, cookies, URL с подписью;
- названия заказчиков, полей, проектов и внутренние номера;
- точные адреса и чувствительные координаты;
- фотографии, видео, документы и вложения, если они не нужны для схемы.

Правила:

1. Одинаковый актив в связанных образцах получает одинаковый псевдоним, например `drone-pseudonym-01`.
2. Не использовать обратимо вычислимые замены вроде «последние четыре цифры серийного номера», если это позволяет идентификацию.
3. Не удалять заголовки/колонки целиком, если они нужны для исследования: вместо этого обезличивать значения, сохраняя тип и формат.
4. Не коммитить реальные журналы в Git-репозиторий и не размещать их в issue, документации или скриншотах.
5. Передавать данные только согласованным защищённым каналом; сам канал и доступы не фиксировать в репозитории.
6. Указать в паспорте, разрешена ли производная тестовая фикстура и где может храниться исходник.

## 5. Фикстуры и тесты

Репозиторий должен содержать только безопасные небольшие фикстуры:

- синтетические CSV/KML для общих сценариев;
- обезличенные минимальные фрагменты реальной структуры — лишь при явном разрешении владельца;
- паспорт фикстуры без персональных данных;
- ожидаемые нормализованные поля, единицы, ограничения и результаты контрактных тестов.

Для каждого одобренного формата будущая фикстура должна проверять:

1. определение типа и версии источника;
2. точное сопоставление подтверждённых колонок;
3. преобразование единиц только по документированному правилу;
4. безопасное игнорирование неизвестных колонок с диагностикой;
5. отказ или статус `unsupported` для неизвестной версии/схемы;
6. отсутствие батарейной оценки для route-only KML;
7. отсутствие `BATTERY_DEVICE_ERROR` без подтверждённой схемы кодов;
8. неизменность нормализованного ожидаемого результата при обновлении адаптера.

Перед добавлением фикстуры необходимо ответить «да» на все вопросы:

- она не содержит персональных, серийных, географических или коммерческих данных;
- есть право хранить её в Git;
- известны источник и версия формата;
- задокументированы единицы и смысл использованных полей;
- тест не утверждает диагноз, который не поддержан входными данными.

Если хотя бы один ответ «нет», использовать синтетическую фикстуру, а исходный файл держать вне репозитория в контролируемом хранилище.

## 6. План исследования после получения данных

1. Проверить паспорт, тип файла, хэш и отсутствие секретов/явных идентификаторов.
2. Зафиксировать наблюдаемую структуру отдельно для каждого источника и версии; не объединять её с общим CSV-парсером по догадке.
3. Описать подтверждённые, вероятные и неизвестные поля в таблице соответствия.
4. Сравнить единицы и диапазоны между несколькими образцами.
5. Создать отдельный адаптер T40 только для подтверждённой версии источника.
6. Добавить contract-тесты на разрешённые безопасные фикстуры.
7. Ввести версию parser/schema/rule profile в результат импорта.
8. Отдельно исследовать DAT/ZIP: лицензионные ограничения, способ получения, контейнер, декодер, воспроизводимость. До успеха оставить статус `unsupported`.
9. Связать `BATTERY_DEVICE_ERROR` только с документированным полем, точными значениями и тестами.

## 7. Подтверждённое, предположительное и неизвестное

| Категория | Состояние |
| --- | --- |
| T40-ориентированный продукт требует реальных расширенных журналов для серьёзной батарейной диагностики | подтверждённое продуктовое ограничение проекта |
| KML/SmartFarm может дать маршрут, но не гарантирует батарейную телеметрию | подтверждённая граница текущего продукта |
| CSV/TXT/KML в frontend-демо имеют общий разбор | подтверждённое поведение текущего кода |
| Конкретные имена полей, единицы, коды ошибок и версии T40-экспортов | неизвестно до реальных образцов |
| DAT/ZIP можно декодировать конкретным способом | неизвестно; поддержка отсутствует |
| Любое CSV warning означает ошибку батареи | неподтверждённое и запрещённое предположение |
| Строки с `cell1...cellN` всегда соответствуют T40 | неподтверждённое; это лишь общий demo-алиас |

## 8. Критерий готовности для начала адаптера

К реализации отдельного адаптера можно переходить, когда есть минимум один разрешённый обезличенный образец определённого источника и версии, его паспорт, таблица полей с единицами и смыслом, безопасная тестовая фикстура или воспроизводимый закрытый тест, а также список ограничений. Для подключения диагностических правил дополнительно нужны подтверждённые входные поля и их связь с правилом.

До достижения этого критерия корректная формулировка интерфейса и API: «файл принят, но подтверждённая аналитика этого формата недоступна».
