## 4. Глобальная дорожная карта разработки

### Этап 1. Укрепить импорт и объяснимость данных

Цель: пользователь должен понимать, почему файл подходит или не подходит для диагностики.

Задачи:

1. Улучшить страницу результата импорта:
   - список распознанных колонок;
   - список отсутствующих критичных полей;
   - подсказка по нужным колонкам CSV/TXT;
   - предупреждение для route-only источников.
2. Добавить кнопку скачивания примера CSV.
3. Добавить кнопку скачивания примера KML.
4. Добавить тесты на пустые/битые CSV/KML.
5. Добавить понятную ошибку для DAT/ZIP: «файл принят, декодер ещё не подключён», без фальшивой аналитики.

### Этап 2. Разделить frontend на нормальные компоненты

Цель: убрать рост `src/App.tsx`, но без большой архитектурной перестройки.

Задачи:

1. Вынести компоненты в `src/components`:
   - `Landing`;
   - `DashboardLayout`;
   - `Overview`;
   - `FlightsView`;
   - `QualityPanel`;
   - `ImportProfile`;
   - `Modal`.
2. Вынести demo data в отдельные файлы при необходимости.
3. После каждого шага запускать:
   - `npm test`;
   - `npm run build`.

### Этап 3. Улучшить аналитику T40

Цель: сделать правила ближе к реальной эксплуатации Agras T40.

Задачи:

1. Добавить отдельный профиль `Agras T40`:
   - напряжение пакета;
   - температура;
   - ячейки;
   - предупреждения;
   - циклы батареи, если будут в данных.
2. Добавить понятие confidence:
   - low;
   - medium;
   - high.
3. Добавить историю батареи:
   - сравнение с предыдущими полётами;
   - персональная норма просадки;
   - тренд деградации.
4. Добавить тесты на все новые правила.

### Этап 4. Подготовить backend

Цель: перейти от демо к реальному продукту, но без резкой ломки frontend.

Рекомендуемая модель данных:

- organizations;
- users;
- drones;
- batteries;
- flights;
- telemetry_imports;
- risk_alerts;
- maintenance_tasks;
- plans/subscriptions;
- analysis_usage.

Рекомендация по стеку backend пока не зафиксирована. Перед выбором нужно сравнить:

- Node/NestJS или Fastify;
- PostgreSQL;
- Prisma или Drizzle;
- on-prem сценарий для РФ-клиентов.

Telegram не использовать.

### Этап 5. Настоящая авторизация и тарифные лимиты

Цель: заменить localStorage-демо на реальный multi-tenant продукт.

Задачи:

1. Организации и пользователи.
2. Роли:
   - владелец;
   - инженер;
   - пилот;
   - наблюдатель.
3. Лимиты по тарифам:
   - количество дронов;
   - количество анализов в месяц;
   - SLA/on-prem для Enterprise.
4. История анализов и загрузок.

### Этап 6. Product polish и подготовка к пилоту

Цель: сделать продукт понятным для первых пользователей.

Задачи:

1. Онбординг: «какой файл загрузить первым».
2. Примеры файлов.
3. Страница «что можно диагностировать».
4. Экспорт отчёта PDF/HTML.
5. Уведомления без Telegram:
   - email;
   - web push;
   - webhook;
   - SMS при необходимости.

## 5. Правила разработки

1. Не делать большие переписывания без необходимости.
2. Не имитировать реальную диагностику при нехватке данных.
3. Любое изменение аналитики покрывать тестами.
4. После значимых изменений запускать:

```bash
npm test
npm run build
```

5. Перед push желательно запускать:

```bash
npm audit --omit=optional
git status --short --branch
```

6. После успешного шага:

```bash
git add .
git commit -m "краткое описание"
git push
```
