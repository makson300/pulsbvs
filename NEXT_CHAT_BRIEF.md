## 5. Глобальная дорожная карта разработки

### Этап 1. Импорт и объяснимость данных — завершён

Реализованы паспорт импорта, список распознанных и отсутствующих полей, шаблоны CSV/KML, защита от пустых и повреждённых данных, а также честная обработка DAT/ZIP без имитации анализа.

### Этап 2. Основание первого пилота: активы и история импортов — завершён в frontend-демо

Реализованы доменные типы `DroneAsset`, `BatteryAsset`, `SavedTelemetryImport`, localStorage-хранилище `puls-bvs-fleet-state`, выбор дрона и батареи при импорте, добавление демо-дронов/батарей, история поддерживаемых импортов, открытие сохранённого анализа после перезагрузки, sidebar footer fix и структурный refactor `App.tsx`.

Ограничения этапа: это локальный frontend-контур без backend/БД; DAT/ZIP не создают полноценную запись истории, пока нет подтверждённого декодера. Подготовительные [API-контракты](docs/BACKEND_API_CONTRACT_V1.md), [ADR](docs/adr/0001-node-postgresql-backend.md) и [требования к T40-журналам](docs/DJI_AGRAS_T40_ANONYMIZED_LOG_REQUIREMENTS.md) готовы, но production-контур и адаптер отсутствуют.

### Этап 3. Достоверный адаптер DJI Agras T40

Цель: заменить универсальные предположения подтверждённой схемой реального журнала T40.

1. Получить обезличенные реальные журналы и описать происхождение, версию ПО, единицы и доступные поля.
2. Написать отдельный адаптер и диагностику неизвестных/изменившихся колонок.
3. Ввести версионируемый профиль T40: обязательные поля, диапазоны, пороги и ссылки на источники правил.
4. Подключить ошибки батареи только по подтверждённым кодам/строкам журнала.
5. Добавить фикстуры реальных обезличенных логов и контрактные тесты.

Критерий готовности: каждый вывод показывает фактические входные данные, версию правила, confidence и ограничение данных.

### Этап 4. История батареи и обслуживание

Цель: перейти от разового triage к раннему выявлению ухудшений.

1. Хранить полёты, циклы, напряжения, температуру, разбаланс, расход и нагрузочный контекст по батарее.
2. Рассчитывать личную норму только по достаточной выборке сопоставимых полётов; иначе честно показывать нехватку данных.
3. Добавить объяснимые тренды батареи и историю решений инженера.
4. Создавать задачи ТО из алертов, вести статусы, исполнителя и подтверждающие документы/заметки.
5. Добавить расписания ТО по налёту, циклам и календарю, начиная с ручной настройки.

### Этап 5. Операционная готовность и отчётность

Цель: дать инженеру и руководителю проверяемый инструмент для пилота.

1. Карта маршрута и временная шкала только по доступной телеметрии.
2. Отчёты по полёту, батарее и ТО с фактическими данными, алертами и ограничениями.
3. Экспорт HTML/PDF/CSV, история действий и хранение оригинала журнала.
4. Уведомления: email и webhook, затем web push. Telegram не использовать.
5. Роли, аудит, политика хранения, резервное копирование и наблюдаемость.

### Этап 6. Масштабирование по подтверждённому спросу

Цель: не повторять AirData целиком, а расширять продукт по результатам пилота.

1. Мультиорганизационность, площадки/проекты и тарифные лимиты.
2. Документированный API и интеграции с BI/GIS/CMMS.
3. Чек-листы, документы, сертификаты и миссии — после интервью с пилотными клиентами.
4. Новые модели БВС — только с отдельными адаптерами, фикстурами и профилями правил.
5. Streaming, погодные модели и сложное планирование — только при измеримом спросе и отдельном техническом обосновании.

Подробный анализ AirData и основания этой последовательности: `PRODUCT_ANALYSIS.md`.

## 6. Правила разработки

1. Не делать большие переписывания без необходимости.
2. Закрывать цельные этапы/пункты с проверкой, не возвращаться к пользователю после каждого мелкого шага.
3. Не имитировать реальную диагностику при нехватке данных.
4. Любое изменение аналитики покрывать тестами.
5. Для UI/import изменений запускать browser smoke через Puppeteer, если dev server доступен.
6. После значимых изменений запускать:

```bash
npm test
npm run build
```

7. Перед push по возможности запускать:

```bash
npm audit --omit=optional
git diff --check
git status --short --branch
```

8. После успешного шага:

```bash
git add .
git commit -m "краткое описание"
git push
```

## 9. Первый рекомендуемый шаг в новом чате

Начать с перехода от локального демо-контура к достоверному пилоту T40, но не писать backend наугад.

**Минимальный полезный инкремент завершён документально: API contracts + backend ADR + требования к реальным T40 логам.**


## 10. Если новый чат начинается после этого memory-pass

1. Проверить, что последний commit/push с сообщением вроде `Update handoff memory for next chat` присутствует в `git log --oneline -5`.
