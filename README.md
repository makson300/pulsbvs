# Пульс БВС

Первый интерфейс и аналитическое ядро платформы контроля флота БВС. Проект намеренно начинает с проверки качества данных: выводы строятся только по полям, действительно присутствующим в импортированном журнале.

## Запуск

```bash
npm install
npm run dev
```

Для production-сборки:

```bash
npm run build
```

Для браузерной проверки разграничения демо и реальных файлов:

```bash
npm run test:browser
```

Сценарий запускает локальный Vite-сервер, очищает `localStorage` между проверками и подтверждает, что синтетический пример не попадает в историю, поддержанный CSV сохраняется с активами и происхождением, а ZIP остаётся в очереди исследования.

## Стартовый парк и ограничение аналитики

Новые чистые установки демо содержат активы **DJI Avata 2**, **DJI Avata 360** и **DJI Mini 4 Pro**. Они служат только реестром парка: состояние, налёт, циклы и здоровье не показываются, пока нет подтверждённого журнала. Данные, уже сохранённые в `localStorage`, автоматически не изменяются и не удаляются.

Подробный путь получения файлов и правила обезличивания: [Инструкция по получению журналов DJI](docs/ИНСТРУКЦИЯ_ПО_ПОЛУЧЕНИЮ_ЖУРНАЛОВ_DJI.md). Для сценариев без DJI Assistant 2 добавлена отдельная [инструкция по логам с телефона и пульта](docs/ИНСТРУКЦИЯ_ПО_ЛОГАМ_С_ТЕЛЕФОНА_И_ПУЛЬТА_DJI.md). Наличие инструкций не означает, что форматы этих моделей уже поддержаны аналитикой.

## Важное ограничение логов

CSV/TXT и KML обрабатываются только как универсальные источники с ограничениями. Полноценная локальная запись появляется только при наличии хотя бы одной распознанной точки; пустые и неинформативные файлы остаются на проверке. DAT/ZIP/JSON не декодируются «наугад»: они попадают в очередь исследования, не анализируются и не становятся полноценной записью истории, пока не подтверждены конкретный источник, схема и отдельный декодер. Для Avata 2, Avata 360 и Mini 4 Pro адаптеры, профили правил и диагностическая поддержка ещё не реализованы.

Правила в `src/analytics/batteryRisk.ts` — консервативная первичная триаж-оценка, а не допуск к полёту и не замена требований DJI или диагностики специалистом. Универсальный разбор не применяет фиксированный порог низкого напряжения: такой вывод возможен только для отдельного подтверждённого профиля батареи с явно заданным порогом.

## Операционный контур и журнал полётов

В демо также работают паспорта дронов и батарей, ручные задачи обслуживания, события, учёт сроков документов, сводка готовности и отчёт. Есть ручные календарные регламенты: пользователь сам задаёт дату следующего срока и при необходимости период в днях; это напоминание, а не телеметрия, диагностика или автоматический допуск. Задачам можно назначить ответственного, завершить их с результатом или отменить; события можно связать с ручным вылетом и закрыть с пояснением. Записи, документы и вылеты можно уточнять или удалять; при удалении вылета его чек-листы удаляются, а связанные события сохраняются без ссылки. Отдельный раздел **«Журнал полётов»** предназначен для ручной записи вылета и предполётного/послеполётного чек-листов. Эти данные сохраняются только в браузере, не являются техническим журналом и не подменяют анализ телеметрии. Отчёты фильтруются по периоду и активу, доступны в текстовом и CSV-виде.

## Статус и направление разработки

Сейчас это frontend-демо с рабочим импортом CSV/TXT/KML, проверкой качества данных, первичными правилами батарейных рисков, реестром активов, историей поддерживаемых импортов, операционным учётом и очередью исследования неподдержанных файлов в `localStorage`. `src/App.tsx` оставлен компактным оркестратором, крупные UI-блоки вынесены в `src/components`. Правила в `src/analytics/batteryRisk.ts` не должны применяться к журналам Avata/Mini без подтверждённого профильного адаптера. Настоящих пользователей, базы данных и производственного backend пока нет.

Актуальное сопоставление с AirData, границы первого пилота и пересмотренная дорожная карта находятся в [PRODUCT_ANALYSIS.md](PRODUCT_ANALYSIS.md).

Backend пока не реализован. Для следующего этапа подготовлены проектные документы:

- [Контракт API будущего backend v1](docs/BACKEND_API_CONTRACT_V1.md): организации, пользователи, активы, импорты, полёты, алерты и задачи ТО.
- [ADR 0001](docs/adr/0001-node-postgresql-backend.md): единый Node.js backend, PostgreSQL, миграции, хранение оригиналов, аудит и требования on-prem.
- [Требования к обезличенным журналам DJI Agras T40](docs/DJI_AGRAS_T40_ANONYMIZED_LOG_REQUIREMENTS.md): происхождение, версии ПО, единицы, поля и безопасные фикстуры.
- [Инструкция по получению журналов DJI](docs/ИНСТРУКЦИЯ_ПО_ПОЛУЧЕНИЮ_ЖУРНАЛОВ_DJI.md): проверенные пути получения журналов Avata 2, Avata 360 и Mini 4 Pro.
- [Инструкция по логам с телефона и пульта](docs/ИНСТРУКЦИЯ_ПО_ЛОГАМ_С_ТЕЛЕФОНА_И_ПУЛЬТА_DJI.md): быстрый сбор FlightRecord через DJI Fly/пульт, ограничения таких данных и карточка происхождения лога.

Эти документы не означают, что backend, декодер DAT/ZIP/JSON или подтверждённый адаптер T40 уже существуют.
