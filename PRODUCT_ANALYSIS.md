# Пульс БВС — продуктовый и технический анализ

Дата анализа: 31 июля 2026. Документ основан на текущем исходном коде репозитория и публичных страницах AirData. Он фиксирует направление разработки, а не заявляет о реализованных возможностях.

**Постоянная граница:** «Пульс БВС» работает исключительно с гражданской авиацией. Военные, оборонные, боевые, оружейные и неотделимые от них сценарии не являются продуктовым рынком, предметом исследований или будущих линеек.

## 1. Роль AirData как ориентира

AirData полезно рассматривать не как список экранов для копирования, а как зрелый операционный контур:

```text
сбор журналов -> привязка к активам -> анализ риска -> обслуживание -> уведомление -> отчёт и аудит
```

По официальным материалам AirData в этот контур входят автоматический сбор логов, детальный разбор полёта, здоровье батарей, обслуживание, пороговые уведомления, учёт пилотов/активов, планирование и отчётность. Для enterprise-сценариев также заявлены роли, организации, чек-листы, документы, API и стриминг. Это ориентир зрелого продукта, но не ближайший объём разработки для «Пульса БВС».

## 2. Что фактически готово в «Пульсе БВС»

### Рабочее ядро демо

- Vite + React + TypeScript приложение с тёмным русскоязычным интерфейсом.
- Локальная демо-сессия через `localStorage`; настоящих пользователей и организаций нет.
- Импорт CSV/TXT как табличной телеметрии и KML как маршрутного источника.
- DAT/ZIP принимаются честно: декодер не подключён, аналитика не запускается.
- Паспорт импорта, Data Quality Score, список найденных и отсутствующих полей, примеры CSV/KML для скачивания.
- Консервативные первичные правила батарейного triage: ограниченность данных, температура, напряжение пакета, разбаланс ячеек, быстрый разряд.
- Unit-тесты парсинга, правил и доменной модели: последний подтверждённый результат — 36 тестов.
- Для новой пустой установки реестр активов начинается с DJI Avata 2, DJI Avata 360 и DJI Mini 4 Pro; без журнала у них нет вымышленных налёта, здоровья или циклов. Существующий `localStorage` не мигрируется автоматически.

### Что является только демонстрационным представлением

- Демо-дроны и демо-батареи, а также введённые пользователем ручные вылеты, задачи ТО, события и документы сохраняются в `localStorage`. Это локальный демо-контур без серверной достоверности и аудита; ручные записи не становятся телеметрией.
- Карточка флота показывает число активов и сохранённых журналов, но не выдаёт оценку здоровья без подтверждённых данных.
- Поддерживаемые CSV/TXT/KML импорты уже сохраняются в локальную историю `localStorage` и связываются с выбранными демо-дроном и батареей; DAT/ZIP не создают полноценную историю, оригинальный файл и серверная неизменяемая запись пока не сохраняются.
- Уведомления, настройки, заявки и карточки сущностей пока являются модальными сообщениями, а не бизнес-процессами.
- Тарифы — демонстрационные: реальные лимиты и биллинг отсутствуют.

## 3. Технические пробелы, важные до обещаний «предиктивности»

1. **Идентичность активов есть только в локальном демо.** Входной поддерживаемый лог связывается с демо-дроном и батареей в `localStorage`, но ещё нет серверной идентичности, пилота, площадки, миссии и аудируемой записи.
2. **История пока локальная и недостаточная для предиктивных норм.** История импортов хранится в браузере, но правило персональной нормы просадки не рассчитывается: нет backend-выборки сопоставимых полётов и соответствующие поля в `BatterySnapshot` не заполняются.
3. **Часть правил не подключена к импорту.** Поля предупреждений CSV распознаются, но `knownBatteryError` в `BatterySnapshot` не устанавливается. Поэтому правило `BATTERY_DEVICE_ERROR` пока не срабатывает по загруженному логу.
4. **Профили батарей пока не формализованы.** Универсальный разбор намеренно не применяет фиксированный порог низкого напряжения: он возможен только при явном пороге в подтверждённом профиле батареи. Нет модели профиля аппарата/батареи, версионирования порогов и проверки модели по реальному логу.
5. **Нет точного адаптера реального источника T40.** Универсальные CSV-алиасы полезны для демо, но производство требует образцов реальных журналов с документированным происхождением и отдельного адаптера. DAT/ZIP не должны декодироваться «наугад».
6. **Нет производственного контура.** Нет API, БД, фоновой обработки, контроля доступа, аудита, резервного хранения оригиналов, лимитов, наблюдаемости и политики хранения данных.

## 4. Сопоставление с AirData: что брать, а что отложить

| Контур AirData | Состояние «Пульса БВС» | Решение |
| --- | --- | --- |
| Импорт и разбор журналов | Начат: CSV/TXT/KML, качество данных, DAT/ZIP без имитации | Довести через реальные журналы конкретной модели и отдельные адаптеры |
| Карточки дронов и батарей | Есть локальные демо-активы и добавление записей через UI | Перенести в backend-контур и добавить аудит |
| Тренды батарей и ресурс | Есть история импортов, но нет сопоставимой серверной истории батареи | Второй продуктовый приоритет |
| ТО по налёту/циклам/календарю | Есть локальные ручные задачи, события, документы и статусы; нет автоматических расписаний по подтверждённой телеметрии | Добавить правила по налёту/циклам только после хранения сопоставимых полётов |
| Уведомления по порогам | Правила есть только в интерфейсе | Ввести после задач ТО; email/webhook, без Telegram |
| Отчётность и экспорт | Есть локальные TXT/CSV-сводки только по ручным операционным данным | Добавить HTML/PDF/CSV-отчёты по подтверждённым импортам и активам в production-контуре |
| Роли, организации, аудит | Нет | Обязательны до multi-tenant пилота |
| Планирование миссий, чек-листы, документы | Ручные предполётные/послеполётные чек-листы и учёт документов есть локально; планирования миссий нет | Не расширять до подтверждения спроса; ручные записи не заменяют телеметрию или допуск к полёту |
| Live streaming, airspace, погодные/ветровые модели | Нет | Не включать в MVP: высокая интеграционная стоимость и нет подтверждённого спроса |

## 5. Целевой MVP для первого пилота

Не «полный российский AirData», а доказуемый контур контроля гражданского DJI-флота. Сначала — получение журналов реального парка (Avata 2, Avata 360, Mini 4 Pro), затем один подтверждённый адаптер. T40 остаётся отдельным будущим гражданским агропрофилем, когда появятся его данные, правовая оценка и подтверждённый workflow.

### Пользовательский результат

Инженер загружает поддерживаемый журнал, указывает или выбирает дрон и батарею, получает прозрачную оценку качества и рисков, а система сохраняет полёт в историю актива. При срабатывании правила создаётся прослеживаемая задача ТО. По батарее можно увидеть факты и тенденции только при достаточном количестве сопоставимых полётов.

### Границы MVP

- Одна организация, роли: владелец, инженер, пилот, наблюдатель.
- Активы: дрон, батарея, импорт, полёт, алерт, задача ТО.
- Поддерживаемый путь: CSV/TXT только после документирования схемы конкретного источника; KML — только для маршрута.
- Сохранение оригинала, нормализованной телеметрии и результата анализа с версией правил.
- Карточки активов, история, базовые тренды и задачи ТО.
- Экспорт отчёта по импорту/батарее в HTML или PDF; email и webhook как будущие каналы уведомлений.

Не включать в MVP: декодирование неизвестных DAT/ZIP, live streaming, биллинг, автоматическое решение о допуске к полёту и регуляторные обещания без юридической и предметной валидации. Каждая новая модель требует отдельного адаптера, тестовых журналов, профиля правил и подтверждённого гражданского назначения.

## 6. Переписанная дорожная карта

### Этап A. Основание пилота: модель активов и импорт — выполнен в frontend-демо

Результат: единичный анализ поддерживаемого CSV/TXT/KML теперь становится локальной прослеживаемой записью. Выделены доменные типы для дрона, батареи и сохранённого импорта; добавлены демо-активы, выбор дрона/батареи при импорте, история импортов в `localStorage` и открытие сохранённого результата после перезагрузки. Синтетические сценарии технически отделены от импорта: они помечены как пример, не связаны с активами и не сохраняются в историю.

Оставшиеся ограничения: это не production-хранилище; оригинальный файл, аудит, серверная неизменяемость и пользователи/организации появятся только в backend-контуре. DAT/ZIP не создают полноценную запись истории до подтверждённого декодера.

Подготовка серверного контура завершена документами: [контракт API v1](docs/BACKEND_API_CONTRACT_V1.md) описывает `organizations`, `users`, `drones`, `batteries`, `telemetry_imports`, `flights`, `risk_alerts`, `maintenance_tasks`; [ADR 0001](docs/adr/0001-node-postgresql-backend.md) фиксирует единый Node backend, PostgreSQL, ORM/миграции, хранение оригиналов, аудит и требования on-prem. Это проектирование, а не backend-реализация. Следующий связанный шаг — получить разрешённый обезличенный журнал любой модели текущего парка по [инструкции](docs/ИНСТРУКЦИЯ_ПО_ПОЛУЧЕНИЮ_ЖУРНАЛОВ_DJI.md), подтвердить схему и только затем планировать адаптер/миграции.

### Этап B. Адаптер и достоверность конкретной DJI-модели

Цель: анализировать конкретный подтверждённый источник, а не абстрактный CSV.

1. Получить обезличенные реальные образцы журналов Avata 2, Avata 360 или Mini 4 Pro и описать их происхождение, версию ПО и доступные поля.
2. Написать отдельный адаптер одного подтверждённого формата с диагностикой неизвестных/изменившихся колонок.
3. Ввести версионируемый профиль выбранной модели: требуемые поля, диапазоны, единицы, пороги и ссылки на источник каждого правила.
4. Подключить предупреждения лога к `BATTERY_DEVICE_ERROR` только по подтверждённым кодам/строкам.
5. Добавить фикстуры реальных обезличенных логов и контрактные тесты; DAT/ZIP поддерживать лишь после отдельного исследования формата и юридических ограничений.

Критерий готовности: каждый вывод по выбранной модели показывает входные поля, версию правила, степень уверенности и ограничение данных.

### Этап C. История батареи, тенденции и обслуживание

Цель: перейти от разового triage к раннему выявлению ухудшений.

1. Хранить циклы, серийный номер при наличии, температуру, напряжение/разбаланс, расход и нагрузочный контекст каждого полёта.
2. Считать личную норму только из достаточной выборки сопоставимых полётов; иначе показывать «данных недостаточно», а не тренд.
3. Ввести объяснимые тренды: разбаланс, температура, минимальное напряжение, скорость разряда, число алертов.
4. Создавать задачи ТО из алертов, учитывать подтверждение/отклонение инженером и историю выполненных работ.
5. Добавить расписания ТО по налёту, циклам и календарю, начиная с ручной настройки, а не с утверждений об автоматическом допуске. Ручной календарный минимум уже реализован: название, актив, следующий срок, необязательный явно заданный период, ответственный и заметка. Налёт, циклы, автоматическое создание задач и любые выводы о ресурсе остаются отложенными до подтверждённых данных.

Текущий результат frontend-демо: реализованы ручные паспорта дронов/батарей, задачи со статусами, события, учёт документов и календарные регламенты. Просроченный регламент виден как напоминание, но сам не меняет готовность и не создаёт задачу: только явно внесённая задача является операционным фактом. Эти записи не создают автоматических диагнозов и не заменяют историю батарей по подтверждённой телеметрии.

Критерий готовности: инженер видит, почему задача появилась, какими полётами она подтверждена и кто закрыл её.

### Этап D. Операционная готовность и отчётность

Цель: дать пилоту и руководителю проверяемый инструмент, а не только экран аналитики.

1. Карта маршрута и воспроизведение поддерживаемой телеметрии с временной шкалой; не показывать отсутствующие сенсоры как будто они есть.
2. Отчёт по полёту, батарее и ТО: фактические данные, алерты, ограничения и приложенный оригинал.
3. Экспорт HTML/PDF/CSV, шаблоны внутренних отчётов и журнал действий.
4. Уведомления о критичных алертах и просроченном ТО: сначала email и webhook, позднее web push; Telegram исключён.
5. Ролевой доступ, аудит, политики хранения, резервное копирование и наблюдаемость.

Текущий результат frontend-демо: отдельная услуга «Цифровой журнал полётов» хранит ручную запись вылета и два чек-листа; доступна текстовая оперативная сводка. Ручные записи явно отделены от технических журналов, PDF/серверный аудит не реализованы.

Критерий готовности: отчёт можно передать руководителю или клиенту без ручного копирования данных и без неподтверждённых диагнозов.

### Этап E. Масштабирование после подтверждения пилота

Цель: расширять продукт только по подтверждённой потребности.

1. Мультиорганизационность, площадки/проекты, расширенные роли и лимиты тарифов.
2. Интеграции с хранилищем, BI/GIS/CMMS через документированный API и webhook.
3. После внедрённого локального прототипа чек-листов и документов — проверить на пилотах роли, юридически значимое подписание, файлы-оригиналы и требования к срокам хранения.
4. Дополнительные модели БВС и новые адаптеры — каждый для подтверждённого гражданского сценария, с собственной схемой, тестовыми журналами и профилем правил.
5. Live streaming, погодные модели и сложное планирование — только при измеримом спросе и отдельном техническом обосновании.

## 7. Первый следующий инкремент

Локальный контур активов и истории уже проверен, сценарии демо отделены от пользовательского импорта, CSV/TXT-выгрузка экранирует разделители, кавычки и переводы строк, а ручные календарные регламенты хранят следующий срок без ложной технической оценки. Sidebar footer regression исправлена, `src/App.tsx` структурирован на именованные компоненты, project skills сохранены в Git. Для новой пустой установки активы настроены под Avata 2, Avata 360 и Mini 4 Pro без ложной оценки их состояния. Подготовлены API-контракт backend и ADR серверного стека, но backend отсутствует. До получения журналов безопасно автоматизировать браузерную проверку различия демо и реального импорта. Затем получить разрешённый образец журнала одной модели текущего парка по [инструкции](docs/ИНСТРУКЦИЯ_ПО_ПОЛУЧЕНИЮ_ЖУРНАЛОВ_DJI.md), подтвердить схему и не пытаться декодировать DAT/ZIP наугад.
